# 실제 검증 기록

검증일: 2026-11-20. 아래는 실제 명령 실행에서 얻은 결과입니다. 예측한 성능이나 임의로 만든 성공 기록을 사용하지 않았습니다.

## 환경

- Ubuntu / WSL2, Linux 6.18.33.2-microsoft-standard-WSL2, x86_64, glibc 2.43
- GCC 15.2.0, C11, `-Wall -Wextra -Wpedantic -Werror`
- 논리 CPU 12개. 소스와 정적 루트는 `/mnt/c`의 Windows 파일 시스템에 위치
- 테스트 도구: Python 표준 라이브러리, 실제 curl, Apache Bench 2.3, Valgrind 3.26.0

## 실행 결과

| 명령 | 결과 |
|---|---|
| `make test` | C 단위 assertion 92개 통과 + 통합 테스트 40개 통과 |
| `make sanitize-test` | ASan·UBSan 빌드의 assertion 92개 + 통합 테스트 40개 통과, 누수 보고 없음 |
| `make smoke` | 실제 curl로 HTML·CSS·JS·SVG·health·백엔드 A/B·UTF-8 POST 확인 |
| `make valgrind` | C 프록시와 C 백엔드 모두 메모리 오류 0, 종료 시 힙 블록 0, 추가 FD 0 |
| `make benchmark` | 12개 조건 각각 1,000요청, 총 12,000요청 완료, failed 0·non-2xx 0 |

메모리 검사는 프록시와 백엔드를 Valgrind로 각각 실행한 뒤 정적 파일·404·POST·프록시 요청 40건을 보내고 SIGTERM으로 종료했습니다. [원본 로그](../reports/valgrind.txt)에서 `in use at exit: 0 bytes in 0 blocks`, `ERROR SUMMARY: 0 errors`, 표준 입출력 3개만 남은 FD 보고를 확인할 수 있습니다.

Sanitizer 검사와 Valgrind 검사는 위에서 실행한 경로를 검증합니다. 모든 가능한 C 프로그램 동작에 누수가 없다는 수학적 증명은 아닙니다.

## 부하 실측

프런트 작업자 64개, 큐 512개, C 백엔드 2개, 루프백, 각 조건 1,000요청입니다. 클라이언트 keep-alive가 켜져 있어도 프록시와 백엔드 사이 연결은 요청마다 새로 만듭니다.

| 경로 | 동시 요청 | keep-alive 끔: req/s | keep-alive 켬: req/s |
|---|---:|---:|---:|
| 정적 `/` | 1 | 453.17 | 468.90 |
| 정적 `/` | 10 | 2,676.27 | 2,853.24 |
| 정적 `/` | 50 | 2,517.22 | 2,770.09 |
| 프록시 `/api/whoami` | 1 | 1,977.00 | 3,263.05 |
| 프록시 `/api/whoami` | 10 | 7,000.35 | 16,115.78 |
| 프록시 `/api/whoami` | 50 | 7,158.76 | 17,558.34 |

정적 경로는 `/mnt/c`의 HTML 파일을 요청마다 열고, 프록시 경로는 C 백엔드가 작은 JSON을 메모리에서 생성합니다. 본문 크기와 파일 I/O가 다르므로 **표만 보고 프록시가 정적 파일보다 본질적으로 빠르다고 결론 내릴 수 없습니다.** 외부 네트워크·대용량 응답·C10K를 검증한 결과도 아닙니다.

[기계 판독용 전체 결과](../reports/benchmark.json)와 `reports/ab-*.txt`의 원본 출력을 함께 보관했습니다.

## 부하 검사 중 확인한 한계

초기 작업자 8개·동시 연결 10개·keep-alive 조건에서는 1,000요청 중 non-2xx 응답 2개와 약 5초의 지연이 관찰됐습니다. 한 작업자가 연결의 다음 요청까지 기다리는 구조이므로 유휴 연결이 작업자를 차지할 수 있기 때문입니다.

이 사실을 숨기기 위해 프로토콜 동작을 바꾸지 않았습니다. 기본 비교 측정은 최대 동시 연결 50개를 처리할 수 있도록 작업자 64개로 명시했고, `tests/benchmark.py --workers 8`로 작은 풀을 재현할 수 있습니다. 정확히 같은 오류 수가 매번 나오는 것은 아닙니다. 더 많은 연결을 효율적으로 관리하려면 연결 준비 상태 관리나 이벤트 기반 구조로 확장해야 합니다.

## 이식성

실제로 실행한 로컬 환경은 WSL2 Ubuntu입니다. Linux/macOS용 GitHub Actions를 추가했으며 원격 실행 결과는 해당 커밋의 Actions에서 별도로 확인합니다. 로컬에서 macOS를 실행했다고 주장하지 않습니다.
